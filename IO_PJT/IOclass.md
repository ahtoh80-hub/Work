# Полная структура класса IOPoint (Оптимизированная версия с дополнениями)

## 📋 Полная иерархическая структура

```
IOPoint - Точка ввода-вывода в системе автоматизации
│
├── Identification : Identification? - Идентификационные данные точки
│   ├── Code : int? - Порядковый номер строки в списке (из колонки "Код")
│   ├── Area : string? - Номер технологической установки/зоны (1-6 ЦИФР!)
│   ├── Plant : string? - Установка/площадка контекста сигнала; в паре с System определяет идентичность тега (правило F2.8)
│   ├── Title : string? - Номер установки/зоны (функциональное наименование)
│   ├── Loop : string? - Основной технологический контур Main (связывает точки одного процесса)
│   ├── SubLoop : string? - Вложенный субконтур (детализация внутри основного контура)
│   ├── ProcessLoop : string? - Технологический контур (технологическое разделение)
│   ├── Logic : string? - Принадлежность сигнала к логике (Logic No из Excel, например "2701-Z-10001/2701-Z-10101")
│   ├── Tag : string? - Уникальный тег устройства (главный идентификатор)
│   ├── ParsedTag : InstrumentTag? - Распарсенный тег (структурированные компоненты)
│   │   ├── TagArea : string? - Код площадки/завода в теге (1-6 ЦИФР!)
│   │   ├── DeviceClass : string? - Класс прибора (1-5 букв A-Z)
│   │   ├── LoopNumber : string? - Цифровая часть Loop, извлеченная из тега (1-5 цифр)
│   │   ├── TagNumber : string? - Порядковый номер прибора (1-3 ЦИФРЫ!)
│   │   ├── Suffix : string? - Суффикс (модификатор прибора, 0-5 символа)
│   │   ├── FullTag : string? - Исходный тег в полном виде
│   │   └── Separator : char? - Определенный разделитель компонентов (если отсутствовал - null)
│   ├── ProcessTag : string? - Технологический тег устройства (для технологических схем)
│   ├── System : string? - Система управления — произвольная строка (напр. DCS/SIS/GDS/РСУ/ПСБ)
│   ├── IoType : string? - Тип сигнала ввода-вывода (DO - дискретный выход, AI - аналоговый вход и т.п)
│   ├── Controller : string? - Имя контроллера (FCS, SIS, GDS) в системе управления (Например, 2000-S-SC-B01)
│   └── Location : string? - Место установки оборудования (датчика, системы управления, подсистемы и т.п.): LCP, Field, DCS, SIS, GDS, ITCC, MMS, MCC, AUX и т.д.
│
├── Signal : Signal? - Технологические параметры сигнала
│   ├── Service : string? - Технологическое описание сигнала (на русском языке)
│   ├── ServiceEnglish : string? - Технологическое описание сигнала (на английском языке)
│   ├── InstrumentType : string? - Тип прибора/устройства (на русском языке)
│   ├── InstrumentTypeEnglish : string? - Тип прибора/устройства (на английском языке)
│   ├── PID : string? - Название P&ID (Piping and Instrumentation Diagram) для привязки к мнемосхеме
│   ├── SignalType : string? - Тип сигнала (I/O Type): DOR-P, DIR(I)-NAMUR, AIR-LP и др.
│   ├── ExType : string? - Взрывозащита оборудования (Ex.d, Ex.i, Ex.e и т.п.)
│   ├── Subsystem : string? - Идентификатор подсистемы (например, )
│   ├── Auxiliary : string? - Вспомогательный прибор (P Surge Protector, B - Safety Barrier, I - Isolator, D - Signal Splitter, R- Relay)
│   ├── VoltageLevel : string? - Уровень напряжения питания сигнала (например, 24V, 220V)
│   └── PowerConsumption : string? - Мощность потребления контура на данном сигнале (например, 5W)
│
├── Ranges : Ranges? - Диапазоны измерений и уставки аварийной сигнализации
│   ├── Primary : Primary? - Основной диапазон измерения (используется для масштабирования сигнала)
│   │   ├── Min : string? - Минимальное значение шкалы, TEXT (по умолчанию "0"; при валидации конвертируется в число)
│   │   ├── Max : string? - Максимальное значение шкалы, TEXT (по умолчанию "100"; при валидации конвертируется в число)
│   │   └── Unit : string? - Единица измерения (мм, kPa, ℃, %VOL, μS/cm, PH)
│   ├── Secondary : Secondary? - Вторичный диапазон измерения (для пересчета в другие единицы)
│   │   ├── Min : string? - Минимальное значение вторичного диапазона, TEXT (конвертируется при валидации)
│   │   ├── Max : string? - Максимальное значение вторичного диапазона, TEXT (конвертируется при валидации)
│   │   └── Unit : string? - Единица измерения вторичного диапазона
│
│   ├── Alarms : Alarms? - Уставки аварийной сигнализации (значения TEXT, без единиц измерения)
│   │   ├── LL : string? - Авария "Нижний-Нижний" (критичный низкий уровень, остановка процесса)
│   │   ├── LL2 : string? - Второй "Нижний-Нижний" (дополнительный критичный уровень)
│   │   ├── L : string? - Предупреждение "Нижний" (внимание оператора, низкий уровень)
│   │   ├── H : string? - Предупреждение "Верхний" (внимание оператора, высокий уровень)
│   │   ├── HH : string? - Авария "Верхний-Верхний" (критичный высокий уровень, остановка процесса)
│   │   └── HH2 : string? - Второй "Верхний-Верхний" (дополнительный критичный уровень)
│
├── Modbus : Modbus? - F9: данные карты адресации Modbus (колонки M_* перед CBL_*)
│   ├── MapFile : string? - Имя файла карты адресации (напр. "…Register Table Modbus - EBSM102.xlsx")
│   ├── SlaveStation : string? - Slave-станция Modbus (Interface parameters, напр. IMCS EBSM102)
│   ├── SlaveIdMain : string? - Slave ID основной (IP main: адрес/маска/порт)
│   ├── SlaveIdBackup : string? - Slave ID резервный (IP backup)
│   ├── Speed : string? - Скорость обмена интерфейса (speed; для TCP — 100Mbps)
│   ├── Timeout : string? - Таймаут ответа устройства (timeout, мс)
│   ├── PrfDesignation : string? - Project Functional Designation — функциональное обозначение объекта ПЛК
│   ├── PlcTag : string? - PLC Tag/Variable Name — полное имя переменной ПЛК (напр. 1115-PM-101A_STA.MCU)
│   ├── ObjectTag : string? - Базовый тег объекта (PLC Tag до "_") — ключ связи с тегом РСУ
│   ├── Description : string? - Description of the variable — описание переменной в карте
│   ├── Units : string? - Units of measurement — единицы измерения
│   ├── Scale : string? - Scale — шкала
│   ├── LL : string? - Low Low alarm value (карта Modbus)
│   ├── LA : string? - Low alarm value (карта Modbus)
│   ├── HA : string? - High alarm value (карта Modbus)
│   ├── HH : string? - High High alarm value (карта Modbus)
│   ├── Scaling : string? - Scaling factors — коэффициенты масштабирования
│   ├── SigType : string? - Signal type (Impulse/Permanent)
│   ├── RegType : string? - Register type — тип регистра (1/4/6)
│   ├── Address : string? - Address/Bit — адрес регистра или бит (колонка БД: M_Address)
│   ├── AccessType : string? - Access type (Read/Write)
│   ├── DataType : string? - Data type (BOOL / 16-Bit Unsigned / 32-Bit Float…)
│   ├── FuncCode : string? - Function code Modbus (02/03/06)
│   ├── DcsChannel : string? - DCS channel — канал РСУ
│   ├── DcsTag : string? - DCS Tag/Name variable — тег РСУ в карте адресации
│   ├── DcsFunctions : string? - DCS functions — функции РСУ
│   └── Note : string? - Примечание строки карты Modbus (note)
│
├── Cable : Cable? - Кабельное хозяйство (физическое подключение сигнала)
│   ├── Id : string? - Уникальный идентификатор кабеля (по проектной документации)
│   ├── Description : string? - Описание кабеля (назначение, куда подключен)
│   ├── Type : string? - Полный тип кабеля (количество и сечение жил, изоляция, оболочка)
│   ├── Designation : string? - Обозначение кабеля по проектной документации
│   ├── From : string? - Начальная точка кабеля (откуда идет)
│   ├── To : string? - Конечная точка кабеля (куда идет)
│   ├── Length : int? - Длина кабеля в метрах (целое число)
│   ├── Color : string? - Цвет кабеля или цвет изоляции жилы (BK - черный, BU - синий)
│   ├── Pair : int? - Номер пары или жилы внутри кабеля
│   ├── Note : string? - Дополнительное примечание по кабелю (изменения, особые условия)
│   ├── VendorDesignation : string? - Наименование кабеля по документации поставщика
│   ├── Drum : string? - Номер барабана для учета кабеля при монтаже
│   └── Voltage : string? - Напряжение питания для активных устройств (если применимо)
│
├── Equipment : Equipment? - Оборудование контроллера (привязка к аппаратным средствам)
│   ├── CableTecon : string? - Идентификатор кабеля по документации TECON (подрядчик)
│   ├── Mcc : string? - Номер подстанции MCC (Motor Control Center) для моторных сигналов
│   ├── ControlCabinet : string? - Идентификатор шкафа управления (Control Cabinet)
│   ├── MarshallingCabinet : string? - Идентификатор шкафа маршаллинга (Marshalling Cabinet)

│   ├── Chassis : Chassis? - Шасси (стойка) контроллера
│   │   ├── Main : string? - Идентификатор основного шасси (стойки)

│       ├── SlotMain : string? - Номер слота основного модуля

│       ├── Module2Redundant : string? - Идентификатор резервного модуля 2
│       ├── Channel : int? - Номер канала внутри модуля (например, 20, 21)
│       └── Type : string? - Тип модуля ввода-вывода (DI32, DO32P, AI16H и др.)
│
├── Revision : Revision? - Управление версиями и метаданными
│   ├── Number : int? - Номер ревизии (версия данных)

│   ├── AkerRevision : string? - Ревизия от Aker Solutions (если применимо)
```

## 📋 Детальное описание всех классов

### 1. IOPoint (Точка ввода-вывода)

Главный класс, объединяющий все аспекты точки ввода-вывода в системах автоматизации.

| Свойство | Тип | Описание | Обязательность |
|:---|:---|:---|:---|
| `Identification` | `Identification?` | Идентификационные данные точки (тег, контур, номер) | Нет |
| `Signal` | `Signal?` | Технологические параметры сигнала (тип прибора, взрывозащита) | Нет |
| `Ranges` | `Ranges?` | Диапазоны измерений и уставки аварийной сигнализации | Нет |
| `Cable` | `Cable?` | Данные о кабельном хозяйстве (кабель, цвет, длина, маршрут) | Нет |
| `Equipment` | `Equipment?` | Привязка к оборудованию контроллера (шкафы, стойки, модули, каналы) | Нет |
| `Revision` | `Revision?` | Информация о версиях и ревизиях документации | Нет |
| `Extra` | `Extra?` | Дополнительные текстовые поля (данные из Excel вне типовой структуры) | Нет |

| `Title` | `string?` | Номер установки/зоны (функциональное наименование) | `"1401"` | - |

### 3. InstrumentTag (Парсер тегов)

Парсер промышленных тегов с автоматическим разбором структуры.

| Свойство | Тип | Описание | Пример | Ограничения |
|:---|:---|:---|:---|:---|
| `TagArea` | `string?` | Код площадки/завода в теге | `"2701"` | **1-6 ЦИФР!** |
| `DeviceClass` | `string?` | Класс прибора (тип устройства по функциональному назначению) | `"XZY"` | 1-5 букв A-Z |
| `LoopNumber` | `string?` | Цифровая часть Loop, извлеченная из тега (связывает приборы одного процесса) | `"10101"` | 1-5 цифр |
| `TagNumber` | `string?` | Порядковый номер прибора в контуре (уникальный идентификатор) | `"01"` | **1-3 ЦИФРЫ!** |
| `Suffix` | `string?` | Суффикс (модификатор прибора: резервный, основной, часть системы) | `"A"` | 0-5 символов |
| `FullTag` | `string?` | Исходный тег в полном виде (для обратного прослеживания) | `"2701-XZY-10101A"` | - |
| `Separator` | `char?` | Определенный разделитель (автоматически определяется при парсинге) | `'-'` | - |

**Примеры парсинга:**

| Тег | TagArea | DeviceClass | LoopNumber | TagNumber | Suffix |
|:---|:---|:---|:---|:---|:---|
| `2701-XZY-10101A` | `"2701"` | `"XZY"` | `"10101"` | `"01"` | `"A"` |
| `123456-PDT-01001A` | `"123456"` | `"PDT"` | `"010"` | `"01"` | `"A"` |
| `42-FT-123` | `"42"` | `"FT"` | `"123"` | `"123"` | `""` |
| `P-9999` | `""` | `"P"` | `"9999"` | `""` | `""` |
| `123456PDT01001A` | `"123456"` | `"PDT"` | `"010"` | `"01"` | `"A"` |
| `TEMP-12345` | `""` | `"TEMP"` | `"12345"` | `""` | `""` |

### 4. Signal (Технологические параметры сигнала)

Детальная информация о сигнале: тип прибора, взрывозащита, тип сигнала.

| Свойство | Тип | Описание | Пример |
|:---|:---|:---|:---|
| `Service` | `string?` | Технологическое описание сигнала (на русском языке) | `"Распределительный клапан для впуска стирола"` |
| `ServiceEnglish` | `string?` | Технологическое описание сигнала (на английском языке) | `"Styrene Inlet Switch Valve"` |
| `InstrumentType` | `string?` | Тип прибора/устройства (на русском языке) | `"Электромагнитный клапан"` |
| `InstrumentTypeEnglish` | `string?` | Тип прибора/устройства (на английском языке) | `"Solenoid valve"` |
| `PID` | `string?` | Номер P&ID для привязки к схеме | `"2490156-1401-PR007-0101A"` |
| `SignalType` | `string?` | Тип сигнала (I/O Type): DOR-P, DIR(I)-NAMUR, AIR-LP и др. | `"DOR-P"` |

### 5. Ranges (Диапазоны и уставки)

Диапазоны измерений и уставки аварийной сигнализации.

| Свойство | Тип | Описание |
|:---|:---|:---|
| `Primary` | `Range?` | Основной диапазон измерения (используется для масштабирования сигнала) |
| `Secondary` | `Range?` | Вторичный диапазон измерения (для пересчета в другие единицы) |
| `Alarms` | `Alarms?` | Уставки аварийной сигнализации (только значения, без единиц измерения) |

#### 5.1. Range (Диапазон)

| Свойство | Тип | Описание | Пример |
|:---|:---|:---|:---|
| `Min` | `string?` | Минимальное значение шкалы, TEXT (по умолчанию `"0"`; при валидации конвертируется в число) | `"0"` |
| `Max` | `string?` | Максимальное значение шкалы, TEXT (по умолчанию `"100"`; при валидации конвертируется в число) | `"100"` |
| `Unit` | `string?` | Единица измерения | `"%"` |

#### 5.2. Alarms (Уставки аварийной сигнализации)

Только значения уставок; единицы измерения не хранятся (убрано по решению). Значения хранятся как **TEXT** (не-числовое содержимое не теряется); при валидации конвертируются в число.

| Свойство | Тип | Описание | Пример |
|:---|:---|:---|:---|
| `LL` | `string?` | Авария "Нижний-Нижний" (критичный низкий уровень, остановка процесса) | `"10"` |
| `LL2` | `string?` | Второй "Нижний-Нижний" (дополнительный критичный уровень) | `"5"` |
| `L` | `string?` | Предупреждение "Нижний" (внимание оператора, низкий уровень) | `"20"` |
| `H` | `string?` | Предупреждение "Верхний" (внимание оператора, высокий уровень) | `"80"` |
| `HH` | `string?` | Авария "Верхний-Верхний" (критичный высокий уровень, остановка процесса) | `"90"` |
| `HH2` | `string?` | Второй "Верхний-Верхний" (дополнительный критичный уровень) | `"95"` |

**Иерархия уровней:**
```
LL2 ← LL ← L ←─── НОРМА ───→ H → HH → HH2
(крит) (крит) (пред)          (пред) (крит) (крит)
```

## ✅ Ключевые особенности структуры

1. **Все свойства nullable** — гибкость при работе с неполными данными
2. **Автоматический парсинг тегов** — через `ParsedTag` (`TagArea` 1-6 цифр!)
3. **TagNumber — только цифры (1-3)** — строгое правило парсинга; `LoopNumber` = цифровая часть `Loop`
4. **Двойные аварийные уровни** — `LL2` и `HH2` для дополнительной критической сигнализации (без единиц измерения)
5. **Полная иерархия** — от общего `IOPoint` до детальных подклассов
6. **Поддержка любых систем** — `System` — произвольная строка (DCS, SIS, GDS, РСУ, ПСБ и т.п., без enum и без жёсткого списка)
7. **Метаданные источника** — `FileName`, `Author`, `DateEntered`, `DateModified`, `RowNumber` для аудита
8. **Многоязычная поддержка** — описания на русском и английском языках
9. **Технологический тег** — `ProcessTag` для технологических схем
10. **Четкая иерархия Loop** — `Loop` → `SubLoop` → `ProcessLoop`
11. **Вторичные диапазоны** — поддержка пересчета в другие единицы измерения
12. **Резервные поля Extra** — `column1`...`column10` для данных из Excel вне типовой структуры
13. **Квадрирование модулей** — `ModuleRedundant` и `Module2Redundant` — разное оборудование при квадрировании сигнала
14. **ИД из Excel** — `Revision.Count` (TEXT) хранит идентификатор записи источника
15. **Шкалы и уставки — TEXT** — нечисловое содержимое не теряется; конвертация в число выполняется при валидации (без единиц измерения)
16. **История изменений** — служебная таблица `IO_LIST_Audit` («что на что менялось», автор, время) с выгрузкой в Excel; действия: INSERT/UPDATE/DELETE, CriticalError, MarkedDelete (F2.11), TagCleaned (F2.15), Duplicate (F9.1, жёлтый), ModbusWarning/ModbusError (F9.8 — сообщения связывания с картой Modbus, жёлтый/красный). Аудит имеет глобальный переключатель `AuditService.Enabled` (F9.9, чекбокс окна импорта карт): при выключении история не пополняется — в журнале событий остаётся минимизация (только имена затронутых Tag)

### DDL служебной таблицы карты Modbus (`MODBUS_MAP`, F9)

Структура строк `Register Table Function 02/03/06` + `Interface parameters` из файлов
«IMCS TO DCS Register Table Modbus»; `LinkTag` — сопоставленный тег РСУ (`IO_LIST.Tag`;
несколько команд, делящих один Control word, перечисляются через запятую), строки без привязки
хранятся с пустым `LinkTag`. `DcsTag` — ключ связи с `IO_LIST` для кнопки «Обновить адресацию
Modbus» (F9.4): список тегов через запятую; при связывании (F9.3) сюда накопительно дописывается
`Tag` связанной точки (ручной ввод в колонке не затирается, дубли не добавляются), повторные
прогоны не растят список; при импорте M_-поля `IO_LIST` не записываются — их заполняет кнопка
по парам `DcsTag ↔ Tag` (только Modbus-сигналы `IO Type`: `M…`/`COM`, иначе ошибка).
`LinkState` — состояние привязки после связывания (F9.3):
«привязано» / «не привязано» / null (связывание не выполнялось); перед каждым прогоном
`LinkState` и `LinkTag` сбрасываются, после прогона строки без результата помечаются
«не привязано». Повторный импорт того же файла заменяет его строки (идемпотентно).
Сопоставление кандидата со строками карты — гибкое: класс объекта перебирается по шагам
F9.6 (точное написание → таблица эквивалентов `{PM↔M, EM↔E, AGM↔AG, BLM↔BL}` → итеративное удаление
букв класса, минимум 1 буква остаётся; титул и номер — строго), теги сравниваются
в канонизированном виде F9.7 (ведущие нули номера срезаются: `003A` ↔ `3A`); сообщения
связывания («Не связано», ошибки) пишутся в `IO_LIST_Audit` как `ModbusWarning`/`ModbusError`
(F9.8, поле `Modbus`, `System` = «Modbus»).
Роль сигнала F9.10: Service «run signal»/«Run» → `STA.MCU` (наравне с «running»); `MSC`
(`AO-COM`/«speed control») → Function 06 «Frequency Setting» (один сигнал на регистр), `MSI`
(«speed signal») → Function 03 `_OP_F` «Operating Frequency» — ветка проверяется раньше
общей ветки тока `AI-COM → I_A`; если Service без ключевых слов — роль по суффиксу тега
(`MXA…A/B/C` → fault/run/ready, `MII` → ток, `MHS` → команда). У VFD с двумя строками
Function 06 команда привязывается к «Control word … Value:1=Stop,…», к «Frequency Setting» —
только `MSC`.
Все имена в квадратных скобках: `Address`/`Note` — зарезервированные слова JET (колонка
адреса названа `AddrBit`). Существующие таблицы мигрируют через `ALTER TABLE ADD`
(`TableCreator.EnsureServiceTables`).

### DDL служебной таблицы ручных правил связывания (`MODBUS_LINK_RULES`, F9.11)

Пользовательские зависимости «поле IO_LIST ↔ поле `MODBUS_MAP`», применяются в
`ModbusLinkService.Link()` **ПЕРЕД** встроенными ролями `DetectRole` (первое сработавшее
правило с меньшим `Priority` выигрывает; без срабатывания — обычная логика ролей).
`Name` — подпись правила (обязательна; имя попадает в журнал/статистику `RuleHits`);
`IOField` — поле IO-стороны: `Tag` (по умолчанию) / `Service` / `ServiceEnglish` / `IoType` /
`Loop` / `SignalType`; `TagPattern` — шаблон по его значению; `MapField` — любое строковое
поле `ModbusMapEntry` (`Description`, `Scale`, `PlcTag`, `FuncCode`, `Units`, `DcsFunctions`, …);
`ValuePattern` — шаблон по значению этого поля; `FuncCode` — опциональный фильтр Function Code
строки карты (пусто — без фильтра); `Priority` — порядок применения (меньше — раньше, по
умолчанию 100); `Enabled` — вкл/выкл (выключенное хранится в БД, в `Link()` не применяется).

Шаблоны (`TagPattern`/`ValuePattern`, `IgnoreCase`, `ModbusLinkRuleService.Compile`):
(1) начинается с `*`/`?` либо содержит только wildcard-метки → wildcard (анкорный: `*` — любые
символы, `?` — один; пример `*Fault*`); (2) содержит метасимволы regex (`. + ^ $ ( ) [ ] { } | \`)
→ регулярное выражение (примеры `MXA.*A`, `MXA+A`); невалидный шаблон → правило пропускается
с предупреждением в журнале, связывание не прерывается.

Редактирование — окно «Импорт → Правила связывания Modbus...» (валидация перед записью,
`SaveAll` = `DELETE` + `INSERT` одной транзакцией, повтор при блокировке БД); чтение для
связывания — `LoadEnabled` (`WHERE [Enabled] <> 0 ORDER BY [Priority], [ID]`). Таблица
создаётся идемпотентно в `TableCreator.EnsureServiceTables`. Ограничение F9.4 сохраняется:
связь записывается только для Modbus-сигналов (`IO Type` `M…`/`COM`).

```sql
CREATE TABLE MODBUS_LINK_RULES (
  [ID] COUNTER PRIMARY KEY,
  [Name] TEXT(255), [IOField] TEXT(50), [TagPattern] TEXT(255),
  [MapField] TEXT(50), [ValuePattern] TEXT(255), [FuncCode] TEXT(50),
  [Priority] LONG, [Enabled] YESNO
);
```

структура — `SCADA_XML_STRUCTURE.md`; шаблон привязок out → tagname — `Work\Data_Out_пример.xml`;
генераторы — `ScadaTemplateXmlService`, `ScadaDataOutXmlService`). F18: **встроенных (embedded)
копий примеров в приложении больше нет** (`EmbeddedResource` удалены из csproj) — шаблон задаётся
явно: файл (путь настройки или авто-поиск: каталог exe → вверх до 6 уровней в `Work\`) либо
вставленный код (режим «Код»); без шаблона генерация не стартует, статус говорит «укажите файл
или вставьте код». Примеры в `Work\` — только для понимания логики: в шаблоне при генерации
меняются лишь марка приёмника, имена блоков и номера `DataOut`.
`SCADA_MB_SETTINGS` — настройки генерации (Name/Value; ключи: `Policy`
(Contiguous/Cover/FixedSize/Gap — политика пакетирования; Gap — прореха ≤ `MaxGap` остаётся
в пакете, > MaxGap → новый блок), `MaxCount`, `MaxGap` (допустимый промежуток адресов для
Gap; 0 = Contiguous), `DefaultPort`, `DefaultSlaveId`, `DefaultTimeoutMs`,
`TemplateMode` (File/Inline — источник шаблона блоков), `TemplateFilePath`,
`DataOutTemplateMode`/`DataOutTemplateFilePath` (источник шаблона привязок Data_Out),
`DataOutTemplateName` (F16: имя текущего шаблона привязок — идентификатор в
`SCADA_DATAOUT_TEMPLATES`/колонка `SCADA_TYPNO_MAP.Template`; для файла по умолчанию —
его имя без расширения, для вставленного кода — имя спрашивается при сохранении),
`BlockNamePattern` (маска имени блока TCP: токены `{Seq}`/`{Slave}`/`{Station}`/`{Ip}`/`{Func}`;
пусто — историческое имя «цифры шаблона + №»), `BlockNamePatternRtu` (F14: маска имени блока
Modbus RTU — применяется, если мастер шаблона содержит «RTU» в имени; пусто — как
`BlockNamePattern`), `FormatAddress` (F14: True/False — вход Address блока в формате
«регистр + адрес»: FC1→0, FC2→1, FC3→4, FC4→3 + адрес с ведущими нулями, ≥4 знака
(FC3: 1 → 4001, 602 → 4602, 1506 → 41506); адрес ≥ 10000 — как есть; False — сырой
`M_Address`), `PouNamePattern`/`DataOutPouNamePattern` (F17: шаблоны имени POU при
экспорте — основной файл `BufScadaPOUS` (мастер-блоки, один POU) и файл привязок
(по POU на пакет); токены `{Master}` (имя мастера шаблона / имя блока мастера
пакета), `{Seq}`/`{Slave}`/`{Station}`/`{Ip}`/`{Port}`/`{Func}` (в основном файле —
контекст первого пакета, в привязках — своего пакета), `{Date}` (yyyyMMdd)/
`{Time}` (HHmmss) — момент экспорта; пусто — исторические имена «NAME из шаблона»
(`MB_Master_4`) / «имя блока мастера» (`MB_TCP_MASTER_4_1`); дубли POU в файле
привязок → суффиксы `_2`, `_3`),
`BaseT11Id`, `BaseCardId`, `ColumnsPerRow`, `RowStep`, `ColumnStep`); при отсутствии
значения/таблицы — defaults из `ScadaMbGenSettings`; устаревшие ключи F13 v1
(`PulsePeriodMs`, `TimeoutTagName`, `PouName`, `MasterPrefix`, `ArrayPrefix`,
`NoLinkPrefix`, `PouId`, `PouNum`, `ControllerTypeName`, `ControllerId`, `ResourceId`,
`ShowTitles`) игнорируются при чтении и удаляются при сохранении.
`SCADA_MB_SLAVE_RULES` — правила «станция → SlaveId»: в IO_LIST нет числового SlaveId
(в `M_SlaveIdMain` — только IP/маска/порт), поэтому `Station` (`M_SlaveStation`,
IgnoreCase) → `SlaveId` (LONG, 1-255); станции без правила получают `DefaultSlaveId`.
`SCADA_MB_TEMPLATE` — вставленные в окно XML-шаблоны (режим «Код»): строка
`Name` = «current» — шаблон блоков, `Name` = «dataout» — шаблон привязок (F13.1);
тело — `Body` **MEMO** (до 64 КБ; TEXT(255) не хватает на 5 КБ шаблон).
`SCADA_TYPNO_MAP` (F14/F16) — ручное сопоставление «`Typno` (IO_LIST, типовой алгоритм) →
(шаблон привязок, эталон)»: `Typno` TEXT(255) (ключ, IgnoreCase) → `Template` TEXT(255)
(F16: имя шаблона из `SCADA_DATAOUT_TEMPLATES`; **пусто — основной шаблон редактора**
(файл/вставленный код)) → `Exemplar` TEXT(255) (ключ Disc/NAME OnePOU: BOOL/INT/DINT/REAL).
Сигнал **без `Typno` не участвует в генерации F14**
(фильтр `BuildPlan`, счётчик `SkippedNoTypno`); для сопоставленного Typno эталон выбирается
**по маппингу (приоритет)**, Typno без строки — исторический выбор по `M_DataType` с
предупреждением; все Tag с одним Typno получают цепочки своего эталона (по одной цепочке на
тег). Хранилище — `ModbusBlockPlannerService` (`LoadTypnoMap`/`SaveTypnoMap` — полная замена:
строки без Typno/эталона отбрасываются, дубль IgnoreCase выигрывает последний с сохранением
канонического написания первого).
`SCADA_DATAOUT_TEMPLATES` (F16) — именованные шаблоны привязок Data_Out: несколько шаблонов
одновременно участвуют в генерации, `Typno` ссылается на имя шаблона. `Name` TEXT(255)
(имя-идентификатор, IgnoreCase, уникально — сохранение с тем же именем заменяет строку),
`Body` MEMO (XML-тело шаблона на момент сохранения — и для файла, и для вставленного кода;
генерация читает тело из БД и не зависит от наличия файлов), `FilePath` TEXT(255) (путь
файла-источника, справочно; кнопка «Обновить из файла» перечитывает `Body` по нему).
Опознавание мастера в шаблоне блоков (F15): по **имени**, а не по `IsaObjId` —
① блок, чей `Params.IsaObjId` совпадает с `ID` rec `MB_TCP_MASTER`/`MB_RTU_MASTER`
в `ISAOBJSINFO` одного шаблона (само значение ID произвольно: 15003, 17573, … — SCADA
переподставляет его при импорте); ② fallback — блок `GROBJTYPE=37` с именем `Info`,
начинающимся на `MB_TCP_MASTER`/`MB_RTU_MASTER`.
Хранилище — `ModbusBlockPlannerService` (`LoadDataOutTemplates`/`SaveDataOutTemplate`
(замена по имени)/`DeleteDataOutTemplate`).
**F18 — байтовая адресация `DataOut` и шаблоны «на один тип сигнала» (2026-10):** блоки мастера
`MB_TCP_MASTER`/`MB_RTU_MASTER` отдают данные как **массив байт** (`MB_USINT_0_249`, док
«Modbus RTU_TCP block.md»), поэтому индекс `DataOut` везде байтовый — `ModbusBlockPlannerService.
DataOutByteIndex(offset, isBit)`: для FC03/04 смещение привязки в регистрах → `offset*2`
(регистр = 2 байта), для FC01/02 смещение в битах → `offset/8` (биты упакованы в байты);
используется в `M_BusDataOut`/`DataOutExpr`, в историческом простом файле привязок и в генераторе
цепочек (`ScadaDataOutXmlService`): источник(и) эталона получают подряд идущие байты
`[{byteBase}…{byteBase+nSrc-1}]`, **число байт задаёт сам эталон** (float V2 = 4 источника,
16-бит = 2 и т.д. — «последовательность 1,2,3,4 байта согласно шаблону для данного сигнала»);
граница привязки считается в байтах (`byteBase + nSrc − 1 ≥ байт_пакета` → пропуск с
предупреждением). **Fallback единственного эталона:** если нужного типа нет (`Disc`/`NAME` эталона
не совпал с `M_DataType`/Typno), а в шаблоне ровно один эталон — берётся он (предупреждение F18);
наборы «шаблон на один тип сигнала» (например `Data_Out_шаблоны_32-Bit Floating_V2.xml`: `Disc=""`,
`NAME="test"`, цепочка 4 байта → `MB_REGs_TO_REAL_CPU850` → приёмник `MARKA` → марка тега
`_1110_MII_00101`) работают без ручной настройки `SCADA_TYPNO_MAP` (но правило
`Typno → ("", "имя-эталона")` подключает эталон напрямую, без fallback-предупреждения). Пустой
`Disc=""` корректно падает на `NAME`. UI: после «Сохранить настройки» шаблоны перечитываются
(`CheckTemplate`/`CheckDataOutTemplate`) — статус актуален; отмена ввода имени шаблона привязок —
явное сообщение «тело в SCADA_MB_TEMPLATE «dataout», в список не добавлено»; диалог имени — с
Owner (поверх активного окна). **F18.1 — прокрутка окна генерации:** окно при открытии
вписывается в рабочую область экрана и заново центрируется (на невысоких мониторах низ ползунка
ушёл за край — нижние группы, напр. Typno, были недостижимы); колёсико мыши не «залипает» во
внутренних таблицах фиксированной высоты левой колонки («станция → SlaveId», Typno) — после
достижения их конца прокрутка продолжается во внешнем `ScrollViewer` (`LeftScroller`) через
`PreviewMouseWheel` окна; таблицы правой колонки («Превью пакетов»/«Привязки») не затрагиваются.
**F19 — имена блоков = превью, один юнит-мастер из XML-шаблона (2026-10):** `Write` размножает
только основной юнит — «мастер, указанный в шаблоне» (`units[0]`: порядок документа совпадает
с `MasterNameBase` из `Parse`); имя блока мастера пакета — строго `p.MasterName` из плана
(ровно то, что показано в превью), без `ShiftInstanceName` за счёт дополнительных юнитов.
Лишние юниты-мастера (артефакт прошлого экспорта в шаблоне: `ModbusTCP` + `ModbusTCP_2` —
оба `IsaObjId=17573`) **исключаются из результата** с предупреждением `GeneratedXml.Warnings`
(выводится в журнал `Log.Warn("F19: …")` и добавляется в статус экспорта): раньше каждый юнит
размножался на каждый пакет — в файле были дубли (`ModbusTCP_2` ×2), лишний `ModbusTCP_3`
и имена, отсутствующие в превью. Связи юнита клонируются по блокам **своего** юнита
(`activeT11`, а не общий `unitT11Set` — чужие связи больше не копируются с несмапленными
T11), связи исключённых юнитов не попадают ни в клоны, ни в «общие» (`droppedT11`); блоки
и примитивы исключённых юнитов в результат не включаются. **Карточки `ISACARDSINFO`:**
rec копируются только при `cardId`, реально используемом блоками результата (`cardNames` из
`outBlocks`), `Info` rec подменяется именем блока — устраняет «старую привязку 4_1»
(`rec ID=630712 Info="MB_TCP_MASTER_4_1"`: при клонировании k=1 cardId не меняется, и rec
шаблона раньше копировался без переименования); rec исключённых юнитов отбрасываются как
сироты. Приёмка: синтетический шаблон с 2 блоками `GROBJTYPE=37` + 2 пакета → ровно 2 блока
мастера с именами превью, `rec 630712.Info` = имя пакета 1, rec юнита B отсутствует,
1 предупреждение в `Warnings`; одиночный мастер — без предупреждений (регрессия F13–F18).

**F36 — канал подстановки маппинга: колонка/«{}» → имя (Info), литерал → значение (`<IV>`) (2026-10):**

### Правила записи (при импорте Excel)

1. `PTag_*` вычисляются из `Tag` при импорте (`PTag_LoopNumber` = цифровая часть `Loop`, см. §3).
2. Значение `-` в ячейке Excel → NULL; строки-разделители из `-` не импортируются.
3. Единицы уставок из Excel (колонка `Unit2`) **не сохраняются**; при необходимости попадают в `columnN` через ручной маппинг.
4. `REV_DateEntered` (при вставке) и `REV_DateModified` (при изменении) проставляются программой, **не из Excel**.
5. Колонки Excel вне типовой структуры → `column1`…`column10` (ручной маппинг в окне сопоставления).
6. Колонки Excel, не сопоставленные **с колонками таблицы**, в БД не записываются.
7. `IoType` и `SignalType` сопоставляются с разными колонками Excel (ручной маппинг).
8. **`Tag` — обязательное поле маппинга**; без привязки `Tag` запись не выполняется.
9. Автозаполнение (не из Excel): `REV_FileName` — имя файла; `REV_Sheet` — имя вкладки (листа)-источника (F2.16); **`REV_RowNumber` — номер строки Excel, в которой находится `Tag`** (маппингом не переопределяется); `REV_Author` — Windows-логин (`домен\логин`); `Code` = `REV_RowNumber − 1`, если колонка `Code` Excel не сопоставлена.
10. Шкалы (`Range_*`) и уставки (`LL`…`HH2`) — TEXT: нечисловое содержимое сохраняется без потерь; при импорте/валидации выполняется конвертация в число (пробелы удаляются, запятая → точка); не конвертируется — значение сохраняется, выдаётся предупреждение.
11. Каждое добавление/изменение каждого поля фиксируется в служебной таблице **`IO_LIST_Audit`** (действие, поле, старое → новое, автор, время); выгрузка истории — в Excel (см. ТЗ, F7). Помимо полевых изменений туда же попадают служебные записи: задвоение тега между документами `Duplicate` (F9.1) и сообщения связывания с картой Modbus `ModbusWarning`/`ModbusError` (F9.8 — «Не связано», «связь отклонена … не Modbus-сигнал», «DCSTAG не Modbus сигнала», «тег из DcsTag не найден»).
